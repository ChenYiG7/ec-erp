# 01 总体架构设计

## 定位

自研电商 ERP,同时覆盖**国内电商**(淘宝/京东/拼多多/抖店/微信小店/快手/小红书)与**跨境电商**(Amazon/eBay/Shopee/Lazada/TikTok/速卖通/Temu)。
功能来源:启航(国内链路)+ Wimoor(跨境纵深)+ OmniTrade 思路(AI 能力),按自身业务整合。

> 编码规范基线:docs/07-开发规范守则.md(以《阿里巴巴Java开发手册》为基线 + 本项目铁律),写代码前必读。

## 架构定调:模块化单体(不上微服务)

理由:
1. ERP 的瓶颈在业务复杂度,不在并发。用户是内部运营 + 定时拉单任务,不是 C 端流量;
2. 库存/订单/财务天然强一致,微服务下要与分布式事务搏斗,只增成本;
3. 启航 v4.1 自己都从分布式回归单体("无需分布式组件,启动更简单"),是踩坑后的行业反馈;
4. 模块化单体按包分域,后续真要拆(多团队/单域负载爆炸),从清晰分包往外拆成本低。

进程形态:

```
                    ┌────────────────────────────────────┐
   Vue3 前端 ──────▶ │  erp-api (:8088 主应用,单体)        │
                    │  全部业务模块 + 一期内置拉单定时任务   │
                    └───────┬───────────────┬────────────┘
                            │               │ Spring Event(进程内)
                    ┌───────▼──────┐   ┌────▼──────────────┐
                    │  MySQL 9.7.2 │   │ erp-worker (:8089) │
                    │  Redis 7     │   │ 拉单/对账(二期拆出) │
                    └──────────────┘   └────┬──────────────┘
                                            │ PlatformClient SPI(防腐层)
                              ┌─────────────┼─────────────┐
                        淘宝/抖店/PDD…   Amazon SP-API    Shopee/TikTok…
```

- **一期**:只部署 erp-api 一个进程,拉单用 `@Scheduled`;
- **二期起**:拉单量大了再把 erp-worker 拆成独立进程(代码早已隔离在独立模块,拆分只是部署形态变化),隔离平台 API 超时/限流故障,独立重启不影响前台。

## 模块划分与依赖规则

| 模块 | 职责 |
|---|---|
| erp-common | 统一返回体/异常/分页/领域事件 |
| erp-system | 用户/角色/菜单(RBAC 已落地)、字典、通知三渠道(站内+Webhook+邮箱)、配置热更 sys_config;部门/操作审计未做 |
| erp-shop | 店铺、OAuth 授权中心(已落地)、多商户(merchant_id 预留)、拉取日志、平台开关(adapter 级) |
| erp-goods | 商品库(SPU/SKU/分类/品牌)、店铺商品、**SKU 映射绑定**、组合装(评估) |
| erp-order | 统一订单库(已落地)、审核/拆合单/内销订单(未做)、销量日表数据面 |
| erp-inventory | 多仓库存、流水、移动加权成本账(已落地)、安全库存(补货 V2 (s,S) 策略)、库存日快照 |
| erp-purchase | 采购单/入库核销(已落地)、采购建议(AI 工作流已落地)、供应商、1688 对接(四期评估) |
| erp-warehouse | 出入库(已落地)/盘点/调拨单域/库位;跨境头程、装箱(未做) |
| erp-fulfill | 发货单/出库(delivery_order,#11 已落地含回传编排)、电子面单(卡国内资质)、FBA Shipment、海外仓推单、供应商代发(未做) |
| erp-aftersale | 退款/退货/换货/补发 8 态状态机(已落地)、平台同步(脱机)、邮件/评论(未做) |
| erp-finance | 结算报告解析(✅ V1)、多币种(汇率管理 ✅)、利润核算(✅ V1 移动加权,周期口径/预估费用/头程分摊未做)、退款勾稽(✅) |
| erp-ads | 广告抓取分析、竞品监控、动态定价(休眠,卡广告 API 凭证) |
| erp-report | 报表 BI(✅ V1:销售/商品分析/利润看板/库存快照/经营简报/导出)、AI 查询入口归 erp-ai |
| erp-platform-sdk | 平台适配防腐层(SPI + Amazon adapter),**依赖方向只向下** |
| erp-contract | 跨域 API 契约模块(只装接口与 DTO,实现收口 erp-api;查询契约九件 + 动账/存在性/引用计数命令) |
| erp-ai | AI 能力层:Spring AI 2.0(ChatClient/@Tool)+ SAA Graph 工作流 + AgentScope;chat 双通道/异常检测/补货/采购建议/文案生成/选品/agent 双角色/RAG 已落地(2026-09 三期四期分批) |
| erp-api | 主应用入口(:8088),聚合所有业务模块 |
| erp-worker | 拉单 worker(:8089,独立进程形态预留) |

依赖规则(违反即架构腐化):
1. 业务模块之间**一期禁止横向依赖**,跨域调用先在 erp-api 层编排;出现重复需求再引入 `erp-xxx-api` 接口模块;
2. 所有模块只允许依赖 erp-common;仅 erp-shop、erp-fulfill、erp-worker 依赖 erp-platform-sdk;
3. erp-platform-sdk 不依赖任何业务模块(防腐:平台翻译层不感知业务);
4. controller 只能出现在各模块自己包内,erp-api 不写业务代码。

## 三个关键设计决定

1. **SKU 映射表是心脏**:`shop_product_sku.sku_id`(平台SKU → ERP SKU)绑定关系歪了,订单/库存/报表全歪。支持按"商家编码"自动匹配 + 人工绑定兜底。
2. **统一订单模型一开始就带跨境字段**:币种、汇率、申报、履约渠道(SELF_FULFILL / FBA / OVERSEAS_WAREHOUSE)。事后加字段代价十倍。
3. **平台对接走防腐层**:统一 `PlatformClient` SPI + `UnifiedOrder/Product/Refund` 模型,平台差异(国内面单 vs FBA 对账)全部封在 adapter 内。详见 `04-平台对接层设计.md`。

## 演进触发点与预案(2026-09-03 评审定版)

> 三项都已识别但**现在不做**,各自绑定明确的触发点;触发前把方案写死,防止临场拍脑袋。

1. **跨域调用形态(触发点:#4 拉单链路,已落地为 erp-contract)**:"跨域调用在 erp-api 编排"仅在单进程内成立;worker 拆出后,拉单链路(拉取 → 订单落库 → SKU 匹配 → 库存扣减)发生在 worker 进程,对 order/inventory 的跨域调用无处安放。
   落地形态:①被跨域消费的能力保持"稳定方法签名 + DTO 出参"(范例:`ShopService.getShopSession` 返回 ShopSession,entity 不出 Service);②`erp-contract` 契约模块统一收纳跨域接口与 DTO(InventoryChangeApi/GoodsQueryApi/OrderQueryApi 等,实现仍在业务模块),api 与 worker 都依赖契约模块;③新跨域需求一律先进 contract,不再新增分散的 erp-xxx-api 模块。
2. **安全配置归属(触发点:同上 worker 拆分)**:SecurityConfig/JwtAuthenticationFilter 现居 erp-api(单体组装点,业务模块不引 Security starter——该形态一期正确)。worker 拆分时二选一:①下沉 erp-system(auth 组件本就在此)或独立 security 模块,两进程复用;②worker 走内网免认证(仅暴露内部管理端口),SecurityConfig 留守 erp-api。拆分前拍板,**不许复制粘贴一套 Security 配置出来**。
3. **多商户上下文(触发点:多商户需求立项,二期评估)**:表结构已带 merchant_id,一期服务端硬编码 1(`ShopService.createShop`)。立项前新增写表代码统一"服务端固定 merchant_id"写法;立项时先落统一机制——登录态携带 merchantId + Service 写入口统一回填/校验(MerchantContext,ThreadLocal 模式参照 AuthContext),禁止各业务方法散落注入。

## AI 架构(2026-09 定版,详见 `05-技术选型与AI方案.md`)

四层叠加,全部构建在 Boot 4.0.6 之上,**三期/四期已分批落地**(异常检测/补货/采购建议/文案生成/选品工作流 + chat 双通道 + agent 双角色):

```
四期已启用 →  AgentScope Java 2.0(2.0.2 GA)     agent 双角色(SUPPORT/OPS,工具零复制桥接)
三期已启用 →  Spring AI Alibaba 2.0(M1.1)       graph-core 工作流:异常监控/补货/采购/文案/选品
基座(必选) Spring AI 2.0(2.0.1 GA)              ChatClient + @Tool 自然语言查询
底座       Spring Boot 4.0.6(Spring AI 2.0 要求 Boot 4.x)
```

- 模型走 OpenAI 兼容接口,DeepSeek/通义/GLM 可切换(配置在 application.yml);
- **红线:AI Tool 只开放只读查询**,写操作必须人工确认,AI 产出一律落 ai_suggestion 建议表人工采纳,SQL 在 Tool 方法内写死,不让模型自由拼;
- 向量库已落地 SimpleVectorStore(内存余弦 + JSON 文件持久化,零新基建零运维),接口按 VectorStore 编程,后续换 pgvector/Redis 只换实现类;向量不入库,ai_kb_chunk 存正本可重建;
- 版本现状(2026-09-06 Maven Central 复核):Spring AI 2.0.1 GA、AgentScope 2.0.2 GA 已就位;SAA 2.0.0-M1.1 仍为里程碑,后续关注 SAA GA 与 Boot 4.1 GA(预计 2026-11),升级只动根 pom 三个 version 属性。
