## 一、背景与现状(2026-09-10 代码事实)

- 槽位:`erp-aftersale/AftersaleOrderService.java` L227-228 javadoc——「数量预校验(该订单行历史退货累计 + 本次 ≤ **订单行数量**;上限按订单行数量而非发货量,放宽不误拦,精确超退窗口人工低频接受,同 #11 并发超发窗口口径,TODO(#12) 随发货域数据完善后收紧)」。
- 收退件复合事务四步(校验链→条件更新占位 RETURN_RECEIVED→IN_RETURN 动账→实收明细),任一步失败整体回滚。
- **为什么当初放宽**:发货量口径需要 join delivery_order_item 汇总实发,且部分发货期间"退货量>已发货量"合法(先退后到货的窗口),按行数量上限=永不误拦,代价是放过理论超退(退多于发)。
- 对标口径:#11 发货域并发超发窗口同口径(人工低频接受),两域收紧应**同批决策**防口径分裂。

## 二、方案设计(预设,触发后拍板)

### 2.1 目标口径

- 上限从 `订单行数量` 收紧为 `该订单行累计实发量(delivery_order_item 已发合计)` + 容差(拍板,建议 0 或 ±1 防边界抖动)。
- 数据源:发货单明细按 order_item_id 聚合已发数量(进度事实源,未绑定行不参与——**未绑定行意味着实发可能被低估**,这是口径的已知残留风险,登记而非掩盖)。

### 2.2 实现形态

- 预校验 SQL 变更:历史退货累计(from aftersale_return_item)与累计实发(从 delivery_order_item)对齐到同一 order_item_id 粒度比较;只改 AftersaleOrderService 校验链一处 + 对应 Mapper 查询,**不动复合事务四步结构**。
- 配置化:**上限口径做成开关**(`erp.aftersale.refund-cap-mode: ORDER_LINE/SHIPPED`,默认 SHIPPED 新口径,可回退 ORDER_LINE)——口径修正类改动留回退开关是低成本保险。
- 拦截文案:区分"超过订单行数量"(数据异常级)与"超过实发量"(超退拦截级),提示语带两值。

### 2.3 与 #11 并发窗口的一致性

- 收紧后校验与发货动作的并发窗口(发货中退货/退货中发货)依然存在——**窗口内人工低频接受的立场是否延续**是拍板点(建议延续:窗口=秒级竞态,加锁代价大于收益,靠对账兜底);若要收紧到强一致需发货单与售后单跨域行锁,复杂度不成比例,明确不做。
